# UI Specification
**ResortOS AI — Restaurant Booking App**

React 19 + Vite + Tailwind CSS 4 SPA, shipped as an installable **PWA**. **Mobile-only layout** (updated 2026-11-03): one column at phone width (max 28rem, centred on larger screens), no desktop variants. Navigation is a **bottom tab bar**. English only. One app with role-based routes: a `USER` lands in the Diner App and an `ADMIN` lands in the Admin Log Viewer.

## 1. Routes
| Path | Access | Screen | Key elements |
|---|---|---|---|
| `/login` | public | Login | email, password, link to register, error banner |
| `/register` | public | Register | name, email, password, phone (optional), inline validation |
| `/` | USER | **Book a Table** | branch toggle → sector toggle → date picker → slot cards (time window, free tables/rooms, disabled if full or not bookable) → party size (1–50) → special requests → **Confirm** |
| `/bookings/:id/confirmed` | USER | Confirmation | reservation **code** (large, copyable), branch, sector, slot window, tables, party size |
| `/bookings` | USER | **My Bookings** | Upcoming / Past tabs. Each card: code, slot, sector, tables, party size, status badge. Actions on upcoming `CONFIRMED` cards: **Reschedule** (modal: date + slot + party size) and **Cancel** (confirm dialog) |
| `/menu` | public (recommendations need login) | Menu | type tabs (Seasonal Fine Dining / À La Carte), price, allergen chips. Logged in: a "Safe for you" section first |
| `/profile` | USER | Profile | name, phone, allergy tag input, save |
| `/chat` | public (anyone) | **Ask the assistant** | email (required) + phone (optional) once; conversation; reply bubbles; **Book it** button on a read-back; a button per alternative; booking card with the RSV code; one-line notice "Messages are processed by an AI service to make your booking" (D12); errors from the agent shown as-is (busy, limits) |
| `/admin` | ADMIN | **Dashboard** | date picker, branch filter, 4 stat tiles (bookings, covers, cancellations, utilization per sector) |
| `/admin/logs` | ADMIN | **Booking Log** | search box + collapsible filters (branch, sector, status, from/to), paginated **card list** (code, customer, sitting, room, party, status), **Export CSV / JSON**, tap a code → **Detail sheet** (customer, tables/rooms, created at, slot start → end, special requests) |

Any route the role can't access redirects (USER → `/`, ADMIN → `/admin`, guest → `/login`). The admin UI has **no** edit, cancel or create controls.

## 2. State & Data
* **Two API folders, one per service (separation of concerns):**
  * `src/backend-api/`: everything that calls the booking API (`/api/...`): fetch wrapper (session cookie), auth.
  * `src/agent-api/`: everything that calls the booking assistant (`/agent/...` → agent `POST /chat`). No auth; the guest's email goes in each request.
  * Pages import from these folders only; no page calls `fetch` directly.
* **Naming:** folders lowercase, kebab-case when multi-word; React components PascalCase; other files camelCase.
* Fetch wrapper: sends the HttpOnly session cookie (`credentials: "include"`). On a `401` outside `/api/auth/*` it signs the guest out locally and goes to sign-in. No refresh, no retry, no idle timer.
* On page load the session context calls `GET /api/user/me`; a `401` means signed out. Screens keep the data they already show until the next server call.
* No global state library. Use React context for auth and local component state for everything else.
* Dev: Vite proxies `/api` to `http://localhost:4000` and `/agent` to `http://localhost:4300` (both same-origin). Prod: `VITE_API_URL`, `VITE_AGENT_URL`.

## 3. PWA

### 3.1 What it does
A Progressive Web App is the same website, plus two small pieces that let a phone treat it like an installed app:

| Piece | What it does for the guest |
|---|---|
| **Web app manifest** (`manifest.webmanifest`) | Lets the guest add "ResortOS Dining" to the home screen with its own icon. It opens full-screen (`display: standalone`) with no browser address bar, in the brand colours. |
| **Service worker** (`sw.js`, generated by `vite-plugin-pwa`) | Keeps a copy of the app's own files (HTML, JS, CSS, fonts, icons) on the phone. The app opens instantly, even on weak or no signal, and updates itself in the background after each release. |

It does **not** keep any booking data. Every reservation, sitting and menu request goes to the live API (`/api/*` is never cached). When there's no network, the app still opens and says "You're offline. Check your connection and try again." instead of showing a browser error page.

### 3.2 Why it matters for this product
1. **No app store.** Guests are often one-off resort visitors. Asking them to find, download and sign up to a store app for one dinner is a big ask. A link or a QR code on the table card opens the booking page right away, and installing is optional, one tap.
2. **It behaves like an app for returning guests.** Once added to the home screen, it opens full-screen from an icon, so checking "My bookings" or the reservation code at the host stand takes a tap instead of finding a browser tab or an email.
3. **Resort Wi-Fi is unreliable.** Poolside, garden and room signals vary. Because the app shell is stored on the phone, the screen appears immediately, and a dropped connection gives a clear offline message instead of a blank page.
4. **One codebase, instant updates.** There is no separate iOS/Android build, store review or forced update. A fix deployed to the website reaches every installed copy the next time it opens.
5. **Staff can use it too.** A phone or tablet at the host stand can have the admin booking log installed as its own app, opening straight to the day view.
6. **Groundwork for later.** Reminder notifications (out of scope for v1) can use web push to installed PWAs, including on iPhone (iOS 16.4 and later), without building a native app.

### 3.3 Limits (accepted for v1)
* **No offline booking.** Availability changes by the minute, so nothing is booked, queued or shown from cache. This is deliberate (PRD v1 §3.2).
* **iPhone installs are manual.** Safari has no install prompt; guests use Share → Add to Home Screen. Chrome on Android offers an Install button.
* **HTTPS is required** in production for the service worker and for installing (localhost is exempt for development).
* **Not listed in app stores**, so it isn't discoverable there; guests reach it by link or QR code.
* **The icon is a placeholder** until the real logo is supplied (see `resortos-booking-web/DESIGN.md`).

### 3.4 Implementation
* Web app manifest: name "ResortOS Dining", short name "ResortOS", `display: standalone`, `orientation: portrait`, theme `#1E4636`, background `#E4EFF7`, icons 192/512 + maskable + Apple touch icon, all generated at build time from `public/favicon.svg`.
* Service worker: `vite-plugin-pwa` `generateSW`, `autoUpdate`. Precaches the built app shell (Latin `woff2` fonts only, to keep the install small). Navigation falls back to `index.html`; `/api/*` is excluded from both precache and fallback.
* `fetch` failures (no network) surface as `ApiError(0, "You're offline. Check your connection and try again.")`.
* Verified by `tests/e2e/pwa.spec.ts` against the production build: manifest fields, every icon reachable, service worker registers, the app opens with the network off, and offline API errors show the message.
* Sign out lives on the Profile tab (guests) and in the header (admins).

## 4. UX Rules
* Show API `message` strings as-is in error banners. They are written to be user-readable.
* Disable submit buttons while a request is in flight.
* Display times in restaurant local time (`UTC+07:00`), e.g. "Sat 24 Dec, 19:30 – 22:00".
* Prices read `Rp 320.000` (space, dot thousands) on every browser. Built-in currency formatting differs between engines (Safari writes `Rp320.000`), so the app formats prices itself (found by the WebKit e2e run).
* Accessible: labelled inputs, keyboard-reachable drawer/modals, sufficient contrast.

## 5. Test Hooks
* Use accessible roles/labels (`getByRole`, `getByLabel`) in Playwright, not CSS selectors.
* `data-testid` only where no accessible handle exists (e.g. stat tiles).
